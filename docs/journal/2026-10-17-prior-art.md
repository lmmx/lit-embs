# 2026-10-17: Prior Art

"Say how a text changed by correlating parts of one version with parts of another" is
not a new problem. Several separate fields have each solved a piece of it. lit-embs's
contribution would be to combine those pieces for prose documents with embeddings in
the loop. This entry records the work most worth stealing from, what each piece does
well, and where each one breaks for this use case. Bibliographic details and
algorithm parameters below were checked against the papers (ACL Anthology / author
PDFs) on 2026-10-17.

## GumTree: tree differencing with moves

Jean-Rémy Falleri, Floréal Morandat, Xavier Blanc, Matias Martinez, Martin Monperrus.
*Fine-grained and accurate source code differencing.* ASE 2014, pp. 313–324.
doi:10.1145/2642937.2642982. Code: github.com/gumtreediff/gumtree.

GumTree is the standard tool for diffing abstract syntax trees with **move**
detection. Its edit actions are insert, delete, update and move, where a move carries
a whole subtree. Computing the optimal edit script with moves is NP-hard, so GumTree
computes node *mappings* heuristically, then derives the edit script from them with
Chawathe et al.'s algorithm. Mapping happens in two phases:

1. **Top-down (anchor mappings).** A greedy search for isomorphic subtrees, tried in
   decreasing height order, considering only subtrees taller than `minHeight`. When
   several candidates tie, it prefers the pair whose *parents* share the most
   matched descendants.
2. **Bottom-up (container and recovery mappings).** Nodes of the first tree are
   visited in post-order. An unmatched inner node `t1` is paired with the
   same-label candidate `t2` that has the highest
   `dice(t1, t2, M) = 2·|matched descendants in common| / (|desc(t1)| + |desc(t2)|)`,
   if that exceeds `minDice`. That is a *container* mapping. Then, among the
   still-unmatched descendants of a container pair, if both remaining subtrees are
   smaller than `maxSize`, an optimal tree-edit algorithm (`opt`) finds extra
   *recovery* mappings.

Published defaults: `minHeight = 2`, `minDice = 0.5`, `maxSize = 100`.

**Why it is the closest match to "what went where":** the two phases separate
*content identity* (anchors: this text block survived intact) from *structural
identity* (containers: this section is the same section because most of its contents
are). That is exactly the distinction needed to tell a moved section, where anchors
are intact and the container is in a new place, from a rewritten one, where the
container still matches by dice but the anchors were replaced. For markdown trees the
translation is direct:

- label → markdown node type (`h2`, `li`, `p`, …)
- isomorphic subtree → identical normalised text hash (the exact tier)
- leaf similarity → embedding cosine, where GumTree has only label/value equality
- `dice` over matched descendants → whether two *sections* are the same section,
  which also solves the "a heading like *Introduction* means nothing embedded on
  its own" problem noted in mdbed's markdown entry

**Where it breaks:** GumTree's leaf matching is exact or string-based, built for code
identifiers. Prose rewording needs a soft similarity at the leaves, and with soft
leaves the top-down "isomorphic" test needs a softened definition too.

## Vecalign: embedding-based sentence alignment

Brian Thompson, Philipp Koehn. *Vecalign: Improved Sentence Alignment in Linear Time
and Space.* EMNLP-IJCNLP 2019, pp. 1342–1348. doi:10.18653/v1/D19-1136.

Vecalign aligns the sentences of a document with its translation using only sentence
embeddings (LASER in the paper, though the method is not specific to LASER). It does
dynamic programming over a cost matrix and allows **many-to-many** blocks: when
several consecutive sentences sit on one side, they are concatenated before
embedding. That handles splits and merges directly. Three ideas transfer:

- **Normalised cosine cost.** The cost of aligning blocks `x, y` is `1 − cos(x, y)`,
  scaled by the number of sentences involved and normalised by the average cost of
  aligning `x` and `y` against *randomly sampled* sentences from the documents. That
  corrects for "hub" embeddings that are close to everything. Short, generic nodes
  like headings are exactly such hubs.
- **Skip cost as a quantile.** Insertions and deletions cost `c_skip`, but rather
  than fixing a raw value, Vecalign sets `c_skip = CDF⁻¹(β_skip)`: a quantile of the
  distribution of 1–1 costs between randomly paired sentences, computed per
  document pair at alignment time. That is a principled, self-calibrating answer to
  "what similarity threshold means *unrelated*?", which mdbed hardcodes as 0.7.
- **Recursive coarse-to-fine DP.** Average adjacent embeddings to halve each side,
  align at the coarse resolution, then refine only within a window around the coarse
  path. Applied recursively, this gives linear time and space (after Salvador & Chan
  2007's FastDTW). Coarse levels consider only insertions, deletions and 1–1.

**Where it breaks:** dynamic programming over two sequences is **monotonic**. It
assumes order is preserved, which holds for translations. A moved section is
invisible to it, or shows up as a deletion plus an insertion. Vecalign is the right
tool *within* a matched container (sentences inside a matched section mostly keep
their order) and the wrong one at document level.

## WikiWho and TokTrack: provenance across a full revision history

Fabian Flöck, Maribel Acosta. *WikiWho: Precise and Efficient Attribution of
Authorship of Revisioned Content.* WWW 2014, pp. 843–854.

WikiWho processes *every* revision of a Wikipedia article and determines, for each
token, the revision that added it, plus every later deletion and reinsertion. It
splits each revision into a hierarchy of paragraphs → sentences → tokens, checks
for identical reuse of paragraphs and sentences from earlier revisions, and falls back
to a standard text diff only for the units that did not match. Over all revisions it
builds a hierarchical k-partite content graph. Evaluated against a hand-built gold
standard it reaches about 95% accuracy, roughly 10 points above the prior state of the
art (De Alfaro & Shavlovsky) and faster. Implementations exist in Python (`WikiWho` on
PyPI) and Rust (`wikiwho` crate). A follow-up dataset, **TokTrack** (Flöck, Erdogan,
Acosta, arXiv:1703.08244), applies it to the complete English Wikipedia: token-level
provenance and change tracking for every article. That is a large, real record of how
texts change over time.

**Why it matters:** this is the "over time" half of the lit-embs vision, already
working at scale, and its hierarchy-plus-exact-reuse design is the "git
content-addressing" idea taken seriously. The exact tier does most of the work; the
expensive comparison runs only on what is left.

**Where it breaks:** it is purely lexical. A reworded sentence is a deletion plus an
insertion, with no record that one became the other. Embeddings are what would fill
that gap.

## git: the exact and cheap baselines

- **`git diff --color-moved`** (git 2.15, 2017) highlights blocks of lines that
  were removed in one place and added in another. Move detection by exact
  (optionally whitespace-insensitive) line-block hashing.
- **Patience diff** (Bram Cohen) anchors the diff on lines that are *unique* in both
  files, then recurses between anchors. **Histogram diff** extends it to
  low-occurrence lines. The unique-anchor idea is GumTree's top-down phase in
  one dimension.

Together these define the cheapest matching tier: content-addressed exact matches
(hash of normalised text), then unique-anchor ordering. Any embedding tier should only
see what these leave unclaimed.

## Edit-intent datasets: ground truth for evaluation

- **IteraTeR.** Wanyu Du, Vipul Raheja, Dhruv Kumar, Zae Myung Kim, Melissa Lopez,
  Dongyeop Kang. *Understanding Iterative Revision from Human-Written Text.* ACL 2022,
  pp. 3573–3590. doi:10.18653/v1/2022.acl-long.250. 31,631 iterative document
  revisions from Wikipedia, arXiv and Wikinews, with sentence- and paragraph-level
  edits. 4K manually and 196K automatically annotated edit intentions (fluency,
  coherence, clarity, style, meaning-changed).
- **arXivEdits.** Chao Jiang, Wei Xu, Samuel Stevens. *arXivEdits: Understanding the
  Human Revision Process in Scientific Writing.* EMNLP 2022, pp. 9420–9435.
  arXiv:2210.15067. 751 full arXiv papers with **gold sentence alignments across
  versions**, plus span-level edits with intent labels for 1,000 sentence pairs. Their
  neural CRF sentence aligner reaches 93.8 F1. That is a concrete number for a
  lit-embs aligner to be measured against on the same data, and the most directly
  useful evaluation set here. They also frame edit extraction as span alignment and
  show it yields finer-grained edits than a standard diff.
- **Wikipedia edit intentions.** Diyi Yang, Aaron Halfaker, Robert Kraut, Eduard
  Hovy. *Identifying Semantic Edit Intentions from Revisions in Wikipedia.* EMNLP
  2017. An earlier taxonomy of why editors change text, useful for deciding which
  edit classes lit-embs should report beyond moved/edited/added/deleted.

## Assignment machinery

These are not document-specific, but they are the candidate engines for turning a
similarity matrix into an alignment (discussed in
`2026-10-17-node-matching-algorithm.md`):

- **Hungarian algorithm** (Kuhn 1955): optimal one-to-one assignment. Adding dummy
  rows and columns with a fixed "unmatched" cost gives added/deleted nodes for free.
  Exactly one-to-one, so it cannot represent splits or merges.
- **Optimal transport.** Word Mover's Distance (Kusner et al., ICML 2015) applied OT
  to text. Sinkhorn iterations (Cuturi, NeurIPS 2013) make it fast and
  differentiable. The transport plan is a *soft* many-to-many alignment: "60% of
  node X went to Y, 40% to Z". That is a natural representation for splits and
  merges. Unbalanced/partial OT lets mass be created or destroyed, which corresponds
  to added and deleted content.

## Current State

- lit-embs contains no implementation of, or dependency on, any of GumTree, Vecalign, WikiWho, patience/histogram diff, Hungarian assignment, or optimal transport (src/lit_embs/__init__.py:1-2, pyproject.toml:26-28)
- `example/data/` provides one source document and three restructured rewrites with no gold alignments, while arXivEdits provides gold cross-version sentence alignments for 751 arXiv papers

## Missing

- An evaluation harness against arXivEdits gold sentence alignments (reported baseline: neural CRF aligner at 93.8 F1) has no code
- An exact-match (content hash) tier, a unique-anchor tier, and an embedding tier for node matching have no code in lit-embs or mdbed
